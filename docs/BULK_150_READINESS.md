# Bulk Supervised ZIP: Readiness for One Controlled 150-Submission Run

Design and evidence record for `TA-BULK-150`. Subject: the existing Bulk Supervised ZIP workflow, used once, on about 150 student assignments, processed one at a time, with the teacher approving every grade.

This document does not describe the system as ready. The verdict is decided by the strict gate in section 8. It is **NO-GO** at the date below.

- `docs/BULK_150_OPERATOR_PREFLIGHT.md` - the manual preflight and teacher-review procedure for the eventual real batch.

- `docs/BATCH_SAFE_AND_TEACHER_PILOT_GATE.md` - the batch-safe design gate this work is measured against.

## 1. Scope, baseline and method

**Scope.** One controlled real run of about 150 submissions through the existing Bulk Supervised ZIP path, one submission at a time, draft-only, with teacher approval creating every final grade. Out of scope: any new feature, any change to approval semantics, any provider call.

**Baseline.**

| Check | Command (from `apps/api` unless noted) | Result |
|---|---|---|
| Backend tests | `python -m pytest -q` against a disposable PostgreSQL 17.10 started from the repo's portable binaries on `127.0.0.1:55432` with a scratch data directory; storage redirected to a scratch directory | 841 passed, 6 skipped, 2 warnings in 93.78 s |
| Backend lint | `python -m ruff check .` | All checks passed |
| Frontend types | `npm run lint` (`tsc --noEmit`), bundled node v22.14.0 | exit 0 |

| Frontend build | `npm run build` | **Not run** (it rewrites `.next`; no web code was touched) |

**Environment.**

- Disposable database only. The pilot database and `E:\teacher-assistant\data` were never opened. A runner script pinned each test key to its own `bulk150_<key>_test` database, its own storage directory and its own pytest base temp.
- The pilot stack was not running and was not started. No Redis, no `llama-server`, no worker.
- Fakes only. A single in-process `BrainProvider` subclass replaced the model. The only production seam patched is `app.services.bulk_evaluation_service.brain_policy_for_profile`.
- Synthetic data only. Every page, name and answer is generated; provenance tokens replace real text.
- The local Qwen MCP bridge failed to connect for the whole session. No Qwen-derived content exists in this document; all analysis was done directly from the code and from test runs.

**Method.**

1. Seven read-only code readers mapped intake, grading/finalization/export, the operator surface, the state machine, evidence readiness, resource limits, and the existing tests. A critic pass corrected overstated claims (applied in section 4.2).
2. A harness builder produced a fake provider, a synthetic corpus builder, a leak detector and poisoned-ZIP fixtures. Two reviewers attacked the harness; their findings were fixed and re-verified by mutation.
3. Five probe agents (approval and export, intake and limits, evidence integrity, recovery and resume, scale and capacity) each turned a suspected gap into a test.
4. Verdicts per probe: **CONFIRMED_DEFECT** (a strict `xfail` test asserts the desired behaviour and fails), **REFUTED** (a passing regression test shows the behaviour is already right), **POLICY_QUESTION** (founder decision; current behaviour pinned by a passing test), **INCONCLUSIVE** (cannot be shown in-process).

**What "verified empirically" means here.** A claim is marked verified only when a named test or a recorded measurement shows it. A claim from reading code is marked "code-derived". A strict `xfail` is an executable statement of a defect: it fails today for the stated reason, and flips to XPASS (and therefore fails the suite) the moment the defect is fixed, which forces the marker to be removed. The fix wave of 2026-10-12 removed the markers of the cases it fixed: 47 strict-xfail cases remain (about 95 cases, 70 test functions, before it), each mapped to an OPEN or PARTIAL row of 4.2.

**What was not done.**

| Not done | Consequence |
|---|---|

| No model call. | Real per-page latency, call count per script, false-blank rate and prompt-cache behaviour are unmeasured. |

| No frontend build and no browser run. | The UI was read, not driven. Claims about buttons come from component source. |
| No concurrency beyond in-process interleaving. | Multi-worker behaviour is pinned by deterministic interleavings, not by real parallel workers. |

## 2. Architecture and ingestion-path findings

### 2.1 Pipeline as built

New runs always use the **page-read** path: `create_from_zip` stamps `visual_evidence_path=page_read` in `import_manifest`, and `_assert_enabled` refuses any profile that cannot read pages. The older mapping and transcription stages remain in the code and are unreachable for new runs. The documented runbook still describes them (RC-64).

```
teacher browser
  POST /assessments/{id}/bulk-evaluation-runs   (one synchronous multipart request, no timeout or progress)
    _assert_enabled -> _load_references -> _stage_archive -> _inspect_archive
    -> idempotency lookup -> _reject_existing_identifiers
    -> one DB transaction: run row, then per unit _import_unit (copy original, rasterise pages, SubmissionPage rows)
    -> items (one per student x question, status pending, stage read) -> audit row -> single commit
    -> route enqueues run_bulk_evaluation_next_job (RQ)
RQ worker (one Windows SimpleWorker, chained one-unit jobs, retry=None, job_timeout=3600)
  run_next, one durable unit per job, then the job enqueues its successor
    READ unit        one whole script: P page reads (one provider call each, claimed before the call)
                     + at most one whole-transcript assignment call (only if a block has a missing or inferred label)
                     -> derive one AnswerEvidenceAssignment per question
                     -> every answer-bearing item is quarantined evidence_review_required (no review exists yet)
    first finished state: completed_with_exceptions with 0 clean drafts
teacher, per student:  classify every page, assign or blank stray blocks, confirm ownership, confirm review
teacher, per item:     resume_item (one click per student x question)
RQ worker
    GRADING unit     one item: re-check evidence, one grading call -> GradeSuggestion (draft, needs_review=True)
                     confidence >= 0.80 -> graded; otherwise exception (draft kept)
    _finish_processing -> review_ready (stores the review snapshot hash)
teacher: approve_clean (count only; exact snapshot hash and exact id set) -> FinalGrade rows
teacher: results.xlsx (gated on completed or completed_with_exceptions)
```

Properties that matter for 150 students:

- **Read-major order.** Every script is read before any item is graded (`run_next` tries read, then mapping, transcription, grading).
- **Transcript-first.** A fresh transcript cannot be reviewed before it exists, so the first pass can only read. The run ends `completed_with_exceptions` with zero clean drafts; grading starts only after the teacher confirms each transcript and clicks resume per item (RC-68).
- **Grading context is text only.** The grading call receives one question, its rubric and one assignment's text. No student image, identifier or submission id reaches it (code-derived; the harness grader cannot see identity either, which is why a provenance check exists, section 5).
- **Drafts only.** Every `GradeSuggestion` is `needs_review=True`. `FinalGradeService._save_final_grade` is the only `FinalGrade` constructor and is reachable only from teacher HTTP routes (G8).

| Stage | What happens | Limits | Failure behaviour | Verified by |
|---|---|---|---|---|

| Commit | Items, audit row, one `commit` | | All-or-nothing in the database; files of the failing unit left on disk (RC-29) | I::test_a_refused_intake_does_not_block_the_corrected_reupload |

What the import never does: look at page content, use the PDF text layer, detect blank or rotated pages, or check scan quality (`quality_score` is `None`). Every page goes to the vision model.

### 2.4 Error handling

- **Intake.** Only `BulkEvaluationError` becomes a 409 with a message. Every other exception, including a FastAPI `HTTPException` raised by the PDF decoder, becomes a 503 "Bulk evaluation could not be started" naming no file, and is not logged (RC-18).
- **Worker.** `run_next` catches every exception in two identical branches: roll back, charge failed page reads, mark every `running` item of the run `uncertain` with `provider_contract_failure`, pause the whole run with a sanitised 500-character message. Failure isolation is per run, not per item (RC-71). Nothing retries and nothing notifies.
- **Enqueue.** A failed chained enqueue pauses the run and re-raises. A failed enqueue on the resume routes does not (RC-46).
- **Provider.** One HTTP POST per call, zero retries. A timeout is an `unknown_outcome` that only a teacher can reconcile, except for timeouts with an empty message (RC-47).
- **Approval.** Exact snapshot hash and exact id set; one transaction after a pre-check of every draft (RC-03 fixed in wave B).

### 2.5 Observability gaps

- No logging calls exist in the bulk route, service or worker. The only trail is `AuditLog`, readable with psql (`docs/PILOT_MONITORING.md`). No metrics or alerting.
- The operator sees five counters (scripts, processed over total, calls used over limit, clean drafts, exceptions), a status and stage string, `run.error`, and an exception list of raw codes. No roster, no per-item warnings, no elapsed time, ETA or throughput, no per-item timeline (RC-59). `uncertain` and `exception` items are merged without a status field.
- Polling runs only while the status is active (`paused`, `review_ready` and `completed*` stop it), swallows errors, and issues four calls plus `/exceptions` every 5 s with no in-flight guard (RC-61).
- Run status `failed` is never written, so a run that cannot continue shows as `paused`.
- A stalled chain is invisible: nothing reports that no job is queued (RC-57).

## 3. Processing contract

What the workflow must do, what it does today, and where the two differ. Every state and transition below was read from code (`apps/api/app/models.py`, `apps/api/app/services/bulk_evaluation_service.py`) and, where marked, exercised by a named test.

### 3.1 Run state machine

`BulkEvaluationRun.status` has 13 values (`ck_bulk_evaluation_runs_status`). `stage` has 8 (`ck_bulk_evaluation_runs_stage`).

| Status | Written by | Meaning | Reachability |
|---|---|---|---|
| `preflighting` | `create_from_zip` (row created) | Import in progress | Written but never durable: overwritten with `queued` before the single commit |
| `queued` | `create_from_zip` | Imported, waiting for the first unit | Durable initial state |
| `reading` | `_process_read`; `resume`, `resume_item` via `_status_for_pending_stage` | One whole script (all pages, then at most one assignment call) is being read | Reachable |
| `mapping` | `_process_mapping`; `_status_for_pending_stage` | Legacy per-answer mapping stage | Unreachable for new runs: `_assert_enabled` refuses profiles without page reading, so the legacy stages never run |
| `transcribing` | `_process_transcription`; `_status_for_pending_stage` | Legacy per-answer transcription stage | Unreachable for new runs (as above) |
| `grading` | `_process_grading` (start of a unit); `_status_for_pending_stage` | One item (one student, one question) is being graded | Reachable |
| `review_ready` | `_finish_processing` when at least one item is `graded`; `_status_for_pending_stage` when nothing is pending | Processing finished; clean drafts wait for the teacher | Reachable |
| `completed_with_exceptions` | `_finish_processing` when no item is `graded`; `approve_clean` when exceptions remain | Finished for the worker; the teacher can still resume items, approve, and download the workbook | Reachable. This is the first finished state of every fresh run (every item waits for transcript review) |
| `completed` | `approve_clean` when `exception_count == 0` and no item remains | Terminal | Reachable |
| `stopping` | `stop()` | Stop requested; honoured at the next unit start | Reachable |
| `stopped` | `run_next` when `stop_requested` | Stopped; `resume()` allowed | Reachable |
| `paused` | `_pause` (every `run_next` exception, `_require_calls`, call limit reached); `resume()` stale branch; create route and chained job on enqueue failure | Needs a teacher | Reachable |
| `failed` | nothing | Declared in the CHECK; `run_next` treats it as terminal | **Never written** |

Run `stage`: `ingestion` is the construction default and is overwritten with `reading` before the single commit, so it is never durable (like `preflighting`). Durably written on the new path: `reading` (create, `_process_read`, `resume`), `grading` (`_process_grading`), `review` (`_finish_processing`), `complete` (`approve_clean`). `evidence_verification` is **never written**. `mapping` and `transcription` are legacy, except that `resume_item` sets the run stage to `mapping` when the resumed item's stage is `read` (a legacy label on the new path; code-derived).

Active statuses for the one-active-run-per-archive unique index (`ux_bulk_evaluation_runs_active_archive`): `preflighting`, `queued`, `reading`, `mapping`, `transcribing`, `grading`, `review_ready`, `stopping`, `paused`. `completed`, `completed_with_exceptions`, `stopped` and `failed` are outside it.

**Transitions.**

| # | From | To | Trigger | Guard | Notes and gaps |
|---|---|---|---|---|---|
| T1 | (none) | `queued` | `create_from_zip` | Provider preflight, finalized references, all intake caps, no duplicate identifiers | One commit; any failure rolls back (leftover files: RC-29). Route then enqueues the first unit; on enqueue failure the new run is `paused` (not audited) |
| T2 | `queued`, `grading`, `paused` | `reading` | `run_next` → `_process_read` | Not terminal; no `stop_requested`; `calls_used < authorized_call_limit` | `run_next` has **no `paused` guard** (RC-43) |
| T3 | `reading` | `grading` | `run_next` → `_process_grading` | No read-stage item remains pending | Order is read-major: every script is read before any item is graded |
| T4 | `reading`, `grading` | `completed_with_exceptions` | `_finish_processing` | No `pending` item; no `graded` item | Items left `running` by a killed worker are ignored (RC-40). Normal for a fresh run: every item is `evidence_review_required` |
| T5 | `grading` | `review_ready` | `_finish_processing` | No `pending` item; at least one `graded` item | Stores `review_snapshot_sha256` (since wave B the read routes show the live hash, RC-01) and audits `processing_completed` |
| T6 | `completed_with_exceptions`, `review_ready` | `reading` or `grading` | `resume_item` (teacher click) | The item is `exception` or `uncertain`; **no run-status guard** | Each click enqueues another chain (RC-44); also clears `stop_requested` (RC-45) |
| T7 | `review_ready`, `completed_with_exceptions` | `completed` or `completed_with_exceptions` | `approve_clean` | Hash equals the live hash; ids equal the live eligible set | One transaction after a pre-check of every draft (RC-03 fixed); the hash shown is the live one (RC-01 fixed); since wave B a per-item decision on the last undecided draft also completes the run (RC-02 fixed, audit `bulk_evaluation_completed_by_individual_review`) |

### 3.2 Item state machine

`BulkEvaluationItem` is one row per (run, submission, question), unique (`uq_bulk_item_run_submission_question`). 8 statuses, 6 stages in the CHECKs.

| Status | Written by | Meaning | Reachability |
|---|---|---|---|
| `pending` | `create_from_zip`; `resume_item` | Waiting for its stage's unit | Reachable |
| `running` | `_process_read` (every item of the next submission, committed before the provider call); `_process_grading` (one item) | In flight | Reachable; a killed worker leaves it here (RC-40) |
| `clean` | nothing | Declared | **Never written** |
| `exception` | `_quarantine` | Quarantined with one or more exception codes; needs a teacher | Reachable |
| `uncertain` | `_mark_running_uncertain` (any unit exception; stale recovery) | A provider call may or may not have completed; never retried automatically | Reachable; counted as an exception |
| `graded` | `_process_grading` when confidence is at least 0.80 | Clean draft, `needs_review=True` | Reachable |
| `approved` | `approve_clean` | Final grade created by the teacher's approval | Reachable. Individual finalization through the review routes sets `final_grade_id` but not this status (RC-78) |
| `stopped` | nothing | Declared | **Never written** |

Item stages written for new runs: `read` (created as `read`), `grading`, `review`, `complete`. `mapping` is the column default (overwritten at creation) and `mapping` and `transcription` are legacy.

Exception codes written on the transcript path: `missing_answer`, `unreadable_handwriting`, `missing_page`, `page_read_failed`, `unassigned_transcript_block`, `unassigned_ink`, `inferred_question_label`, `evidence_review_required`, `stale_evidence`, `verification_disagreement`, `provider_contract_failure`.

| # | From | To | Trigger | Guard |
|---|---|---|---|---|
| I1 | `pending`/`read` | `running`/`read` | `_process_read` | Next submission by id; budget remains |
| I2 | `running`/`read` | `exception`/`read` | `_process_read` | Assignment missing or not `answer_present` (specific code); or `answer_present` without a current teacher review (`evidence_review_required`) |
| I3 | `running`/`read` | `pending`/`grading` | `_process_read` | Assignment current, `answer_present`, review current (codes cleared) |
| I4 | `exception`/`read` | `pending`/`grading` | `resume_item` | Assignment `answer_present` and review current |
| I5 | `pending`/`grading` | `running`/`grading` | `_process_grading` | Assignment current and `answer_present`; review current; region exists; active rubric exists; `_require_calls(1)` |
| I6 | `pending`/`grading` | `exception`/`read` | `_process_grading` | Any I5 guard fails (`evidence_review_required` or `stale_evidence`) |
| I7 | `running`/`grading` | `graded`/`review` | `_process_grading` | Draft stored and confidence at least `bulk_grading_clean_min_confidence` (0.80). Prior exception codes are not cleared (RC-42) |

### 3.3 Per-submission derived state

A submission has no state column. Its state is derived from its items, its transcript review and its page states. Define it as the least-advanced state among its items; list the per-question states beside it. The workbook marks a student `INCOMPLETE` unless every item is `approved`.

| Derived state | Derivation | Permitted next | Who acts |
|---|---|---|---|
| IMPORTED | All items `pending`/`read`; no `ScriptTranscript` | READING | Worker |
| READING | Any item `running`/`read` | NEEDS_REVIEW, BLOCKED, NEEDS_RECOVERY | Worker |
| NEEDS_REVIEW | Transcript complete; items `exception` with `evidence_review_required`, `inferred_question_label`, `unassigned_transcript_block` or `unassigned_ink`; no current review | READY_TO_GRADE | Teacher: classify every page, assign or blank stray blocks, confirm ownership, confirm review (`confirm_script_transcript_review`) |
| BLOCKED | Items `exception` with `missing_answer`, `unreadable_handwriting`, `missing_page`, `page_read_failed` (assignment state is not `answer_present`) | READY_TO_GRADE after the teacher fixes the evidence and re-derives; otherwise stays `INCOMPLETE` | Teacher (RC-73: no in-product zero for a confirmed blank) |
| READY_TO_GRADE | Review current; items `pending`/`grading` | GRADING | Teacher: one `resume_item` click per item (RC-68) |
| GRADING | Any item `running`/`grading` | DRAFTED, NEEDS_RECOVERY | Worker |
| DRAFTED | Items `graded` (clean) or `exception`/`review` (low confidence) | APPROVED | Teacher: `approve_clean`, or per-item review |
| APPROVED | Every item `approved` or finalized with a `final_grade_id` | none | n/a |
| NEEDS_RECOVERY | Any item `uncertain`: a page `failed`, `unknown_outcome` or `dispatched`; a failed assignment call; a killed grading call | NEEDS_REVIEW or READY_TO_GRADE after recovery | Teacher; dead ends: RC-37, RC-38, RC-39 |

A correction to the transcript, a re-derivation ("Analyze saved transcript") or a reference edit moves the affected items back: drafts are superseded and the review becomes stale, so the submission returns to NEEDS_REVIEW. Since wave B a superseded `graded` item moves to a `stale_evidence` exception (RC-04).

### 3.4 What is persisted for safe resume and idempotent retry

| Persisted | Where | What it guarantees |
|---|---|---|
| Run state, call ledger, stop flag, heartbeat, error, snapshot hash, counts, `import_manifest` (including per-script page-read call baselines) | `bulk_evaluation_runs` | Resume continues from stored state; `calls_used <= authorized_call_limit <= 2000` by CHECK |
| One item per (run, submission, question) with status, stage, codes, warnings, links and three snapshot hashes | `bulk_evaluation_items` | No item can be duplicated |
| Page claim before the provider call (`dispatched`), result after (`succeeded`, `failed`, `unknown_outcome`); blocks; teacher classification | `ScriptPageTranscript`, `ScriptTranscriptBlock`, unique per (transcript, page) | A page read is never repeated silently after an unknown outcome; completed pages are reused at zero cost |
| Versioned assignments with state and spans; one current assignment per (transcript, question) | `AnswerEvidenceAssignment` | Evidence is bound to a transcript version; a re-derivation creates a new version |
| Teacher review: reviewer, time, snapshot hash over blocks, classifications and assignments | `ScriptTranscript` | Grading is blocked unless the review is current |
| One `GradingJob` and at most one `GradeSuggestion` per job; at most one `queued`/`running` job per answer region | `grading_jobs`, `grade_suggestions` (`ux_grading_jobs_active_answer_region`) | No two live grading jobs for one answer |
| Evidence fingerprint on each draft | `GradeSuggestion.source_evidence_fingerprint` | A stale draft cannot be finalized |
| One model lease row (TTL 1,800 s, fail-fast) | `local_model_leases` | One provider call holder at a time |
| Audit rows | `AuditLog` | See 3.6 |

**Not persisted or not guaranteed.**

- Per-item transition history.
- The cause of a pause beyond 500 characters, overwritten by the next pause or resume.
- Which process owns a unit: no owner column; the heartbeat is written at unit start and end only (RC-41).
- Item claiming: selection is a plain read and a status update with no row lock (RC-44).
- The result of a provider call whose reply was lost: recorded only as `unknown_outcome` for page reads; a grading call is a `running` job.
- The cost of a failed grading call (RC-51).
- The RQ chain. A unit is one Redis job that enqueues its successor; a killed worker ends the chain silently, and nothing sweeps (RC-57).
- The roster: `import_manifest` is not exposed by the API.

**Idempotent retry rules that hold.** Re-reading a script uses stored pages at zero calls (Rv::test_pb9_a_unit_arriving_after_another_read_the_script_reuses_the_stored_pages). A page claim cannot be dispatched twice. A terminal grading job returns its stored suggestion. A replayed `approve_clean` is refused. **Rules that do not hold:** a `GradingJob` left active (RC-39), a stale `dispatched` page (RC-37), a re-upload enqueues a second chain (RC-44).

**Per-call timeout.** `LOCAL_QWEN38_TIMEOUT_SECONDS` is configured as 1,800, but the effective timeout of the `llama_cpp_qwen38` profile is **600 s**. `BRAIN_MODEL`, `BRAIN_API_KEY` and `BRAIN_BASE_URL` are set, so `legacy_profile_settings` in `packages/brain/profiles.py` overwrites `local_qwen38_timeout_seconds` with `BRAIN_TIMEOUT_SECONDS` (600). A long page read can therefore time out at 600 s and become `unknown_outcome` (RC-54). The RQ job timeout is a fixed 3,600 s per unit and is a soft limit on Windows (`TimerDeathPenalty`, which cannot interrupt a blocking socket read). The model lease TTL is 1,800 s, refreshed before and after calls.

**Call arithmetic.** One provider call per page read; at most one whole-transcript assignment call per script (fired when any block has a missing or inferred label); one grading call per (student, question). Plus one per re-read of a known-failed page and one per "Analyze saved transcript". Formula, validated against real fake-provider runs (Rv::test_pb7_the_call_formula_matches_what_a_real_run_spends; S::test_call_budget_arithmetic_and_the_two_ceilings):

`calls = pages + scripts_with_continuation_blocks + students x questions`

Before F12 a run authorised for exactly its need ended paused and unapprovable (RC-49); since F12 it finishes. Since W10 intake refuses a limit below pages + items. Whole-transcript assignment calls are not in that minimum, so still authorise the need plus slack for assignment calls and retries (a failed grading call is not charged, RC-51); an exhausted run is still a dead end (RC-48). Worked examples for 150 students:

| Shape (students x pages x questions) | Pages | Calls needed | Against the 2,000 ceiling and the 720-page cap |
|---|---|---|---|
| 150 x 4 x 6 | 600 | 1,500 (600 reads + 900 grades); up to 1,650 with an assignment call per script | Fits. The headline test authorised 1,502 |
| 150 x 4 x 8 | 600 | 1,800; up to 1,950 | Fits only under the 2,000 ceiling. 1,800 equals the *default* server ceiling, so on a default server no slack for assignment calls is possible (exact authorisation finishes since F12, but one assignment call exhausts it, RC-48) and the UI pre-fill of 2,000 is refused (RC-53) |
| 150 x 4 x 9 | 600 | 1,950; up to 2,100 | 1,950 needs the 2,000 ceiling with at most 50 assignment calls. With a continuation in every script, 2,100: impossible |
| 150 x 4 x 10 | 600 | 2,100 | Impossible |
| 150 x 5 x any | 750 | n/a | Refused after about 725 pages were rendered and written (RC-17). 144 students x 5 pages is the largest cohort at that length |
| The only recorded real script (23 pages, 15 questions, `docs/PROVIDER_REHEARSAL_2026_09_22.md`) | 3,450 | about 5,700 before assignment calls | About 4.8 times the page cap and 2.85 times the call ceiling (RC-52) |

Break-even for N students: `N x (pages + 1 + questions) <= ceiling`. At N = 150 and a 2,000 ceiling: pages + questions at most 12. At a 1,800 ceiling: at most 11. If no script needs an assignment call, one more.

| Limit | Checked | Outcome |

Anything else that needs the model (reference extraction, OCR, a second run) contends for the same slot (RC-72).

**Time and space.** Measured: eleven `llama-server` log entries for about 2k-token prompts at 38-88 s (mean 58 s, 8.6-11.0 tok/s) and one 5.4k-token call at 248 s. ## 4. Risk register

The register has two views of the same findings. 4.1 is the coverage matrix by risk (R01-R18, the ids used by the code readers). 4.2 is the root-cause register: one row per distinct root cause, deduplicated across seven readers, five probe agents and the harness builder (about 120 probe items and about 120 reader gaps fold into the rows below). 4.3 lists the behaviours that were suspected and proven already right. Sections 2 and 3 describe the workflow as found at the baseline `8a25268`; where a fix of section 9a changed a behaviour they describe (for example RC-18, RC-20, RC-40, RC-43), the Status cell in 4.2 and section 9a say what changed.

Definitions.

- **Severity** is the impact if the defect occurs on a real run. *High*: a wrong, mixed or unauthorised grade can result, student data can be lost or mixed, or the run cannot be completed or recovered without a code change. *Medium*: a wrong or confusing operator outcome that a teacher can recover from by hand. *Low*: unlikely or cosmetic. No source rated any gap critical (a search of every reader gap, probe verdict and critic note finds no "critical" rating).
- **Likelihood** is for one 150-student run on this machine (recorded MTBF 7.4 h, single sequential worker): certain, likely, possible, unlikely, unknown. It is stated separately from severity.
- **How detected**: a *strict xfail* test asserts the desired behaviour and fails (the defect is proven; once the defect is fixed the marker is removed and the test is a plain passing test, called "flipped" below); a *pin* is a passing characterisation test of current behaviour; *code-derived* means no executing test exists (reading only, or a lead measurement).
- **Status**: OPEN (nothing changed), PARTIAL (mitigated; the cell names what remains), FIXED (a strict xfail was flipped to a plain test, or a new test pins the fix; the fix id is named, for example `FIXED (F01)`), FOUNDER-DECISION, REFUTED (the suspected gap does not exist; those rows live in 4.3). At the baseline every row was OPEN or FOUNDER-DECISION. The column below is the state after the fix wave of 2026-10-12 (section 9a). A PARTIAL row is not closed: for gate G2 it counts as open. A FIXED row is closed only for the behaviour its test pins; the qualifier after the semicolon lists what the fix does not cover.

### 5.2 Design

- **Real pipeline, fake model.** `FakeBulkBrainProvider` is a `BrainProvider` subclass with `VISUAL_PAGE_READ`, `OCR_ANSWER_MAPPING` and `GRADING`. The real `_assert_enabled`, `_validate_authorization`, `transcript_review_is_current`, `run_next`, `resume_item`, the review routes and `approve_clean` all run. The teacher gate is driven through the real route functions `classify_script_transcript_page`, `confirm_current_answer_evidence_ownership` and `confirm_script_transcript_review`.
- **Output derived from the image only.** The fake keys its page output on the SHA-256 of the **stored** page image (intake re-encodes every image, so the harness registers pages after import). Grading output depends only on the evidence text it receives.
- **Pixel-based page identity.** The registry identifies each stored page by decoded pixels, not by the database's claim. If the database says page 1 of S001 but the pixels say S002, the harness raises. This closes a hole the first review found (an intake that attached the wrong image to a student stayed green).
- **Provenance tokens.** Every fake block embeds `SYN150|<student>|<question>|p<page>|b<block>`. `assert_no_cross_student_evidence` inspects every assignment span (current and suggestion-bound), the compat region text, every `GradeSuggestion`, the evidence each grading call saw, the span-to-block-to-page-to-transcript-to-submission ownership chain, the item-to-suggestion-to-region links, and (with a corpus) the exact expected token set per question. `assert_every_answered_question_graded` and `assert_continuations_isolated` are separate opt-in checks.
- **Mutation-checked.** The detector was attacked with nine sabotage families; all are detected after the fixes: a two-way block swap between students (M1), rewritten grading evidence (M2), another question's text on a span (M3a-c), a span re-pointed at the other student's byte-identical block (M4a, structural), a suggestion bound to another student's assignment (M4b), suggestions swapped between items (M4c), regions swapped (M4d), a swapped stored image (M5a). A shared page inside a multi-page answer must grade clean (no false positive, M9b).
- **Failure injection.** `Fault(kind, exc, ...)` on `read_page`, `map`, `grade` or `verify` (before any page row exists), `when='after'` (billed but never seen), `transform` (drop a block, hallucinate a label, empty non-blank page, reverse blocks), `callback` and `RecoverMidCall` (a second session ages the heartbeat and presses Recover mid-call, using its own connection pool). `ProcessKilled` is a `BaseException` that no production `except Exception` catches. A `managed_local_phase='Qwen38'` variant runs the real `LocalModelLeaseService`; `hard_kill_skips_lease_release` models `kill -9` for the lease.
- **Strict xfail convention.** A proven defect is `xfail(strict=True, raises=AssertionError, reason="GAP <root-cause>: ...")` asserting the desired behaviour. Setup checks go through `precondition(cond, message)`, which calls `pytest.fail` (not an `AssertionError`), so a broken setup shows as a failure and cannot xfail for the wrong reason. A neutralised-fault experiment (every `Fault` disabled) turned 10 of 12 fault-dependent GAP tests from XFAIL into FAILED, and the other two use no fault by design.
- **Safety rails.** The `bulk_env` fixture sets storage and the bulk feature flags before `get_settings()` is cached and asserts that `get_settings()` agrees with the harness settings. Storage helpers refuse to run without it, including an explicit `storage=` argument. The database fixture refuses any database name that does not end in `_test`, with the same two overrides as `tests/conftest.py` (`TA_ALLOW_DESTRUCTIVE_TEST_DATABASE=true` and `CI=true`: GitHub Actions runs the suite against a service database named `teacher_assistant`). `CLEANUP_MODELS` is checked against `Base.metadata` so no table is missed. `psutil` (used only to report RSS in the scale tests) is not a declared dependency, so it is imported lazily and RSS reads 0 without it. A CI-like run (`CI=true`, a database not named `*_test`, `psutil` import failing) of the seven bulk150 files gave the same result as the normal run: 347 passed, 7 skipped, 47 xfailed. The real GitHub Actions workflow (Ubuntu, PostgreSQL 16) was not run.

### 5.4 Limits of the harness

| Limit | Consequence |
|---|---|
| The grading prompt carries no student identity, so no grader can notice that a complete answer came from another student | Whole-answer substitution is caught only by the provenance checks (`detected_answer_summary` echo, token sets), not by the model |
| The route layer is exercised only in the `TestClient` tests; most tests call the service and the route functions in-process | HTTP routing, RQ enqueueing and the 409/503 mapping are verified only where a `TestClient` test says so |
| `ProcessKilled` is graceful unwinding of a `BaseException`, not `kill -9` | The lease `finally` runs; a real kill, the Windows RQ timeout and a persisted stale job are not exercised |
| The fake never reads real handwriting; pages are small mostly-white PNGs | Page-read quality, omission rate, false-blank rate, disk and memory are floors, not estimates |
| Shared byte-identical pages must have the same page number for both students (the token embeds it) | The identical-pair scenario cannot model different expected pages with identical bytes |
| Provider-construction seam (`BrainAdapter.for_profile`, API-key and data-boundary pins) is replaced | Profile catalog and model-hash pins are not exercised |

### 7.5 Limitations

- **Requirement.** After any kill, restart, re-upload or retry, no record is duplicated, lost or attached to the wrong student.
- **Evidence (holds).** A worker killed between units converges to the uninterrupted result (30 students, four kill plans: two redrain, two stale-heartbeat Resume; digest `5cf7e4ca699b4ab9`). Page claims, the active-job unique index and `retry=None` prevent double reads and double billing in the interleavings tried (4.3). `approve_clean` replay is idempotent. Fixed in the fix wave: a duplicate ZIP member no longer replaces a script (RC-20); a run no longer finishes over a `running` item (RC-40); an identical re-upload returns the existing run and enqueues no second worker chain, and a stray unit cannot un-pause a paused run (RC-44 PARTIAL, RC-43; Rv::test_pb4_an_idempotent_reupload_does_not_enqueue_another_worker_chain, Rv::test_pb4_a_stray_worker_unit_does_not_un_pause_a_paused_run); a pending Stop survives an item retry (RC-45 PARTIAL).
- **Status.** FAIL.
- **Unmet.** Overlapping uploads create every student twice (RC-21). A mid-call kill leaves a dispatched page that nothing recovers (RC-37); after a hard kill the grading retry waits for the dead holder's lease, and the guard that decides a job is dead has latent fail-open cases with a second worker (RC-39 PARTIAL). Two units that selected the same pending item grade it twice and the loser quarantines the winner's finished script (RC-44, two strict xfail, needs a second worker). `stop()` on an idle `paused` or `review_ready` run strands it `stopping`, and Recover cancels a pending Stop (RC-45).
- **Smallest remediation.** An advisory lock in `create_from_zip` (RC-21); the dispatched-page recovery (RC-37); an atomic claim of the pending item and a scoped `_mark_running_uncertain` (RC-44). Section 9b has the order.

### G7. Incomplete evidence cannot proceed as grading-ready

- **Requirement.** Every ambiguity or missing-evidence case becomes "needs teacher review"; none reaches grading on an assumption.
- **Evidence (holds).** Five gates enforced server-side: no current assignment; assignment not `answer_present`; transcript review not current; a re-check immediately before the provider call; the grading service's own checks (3.5). ## 11. Limitations and open questions

- **No model evidence.** Every number is pipeline overhead. Real latency, call counts per script (assignment calls), omission and false-blank rates, prompt-cache behaviour and cross-student KV-cache isolation in the single-slot server (RC-62) are unmeasured.
- **No real archive.** Pages per student, scan resolution, ZIP size, naming and tool of origin are unknown. The 720-page cap and the call ceilings are judged against assumed shapes.
- **No stack.** The RQ job timeout on Windows, queue persistence across a hard reboot (since W04 a stale queued job can no longer un-pause a paused run; what it does to a `queued` or active run was not exercised), launcher restarts and a real `kill -9` were not exercised. The harness's `ProcessKilled` is graceful.
- **No browser.** UI behaviour is read from source. Whether the review screen shows each page image next to its transcript, and how likely a reviewer is to notice an omitted paragraph across about 600 pages, is not measured.
- **Live configuration.** `.env.local-ai` was not read by the analysis; the effective limits come from instantiating `Settings` with the launcher's layering on this machine's `.env` files, and the operator must confirm them (RC-53, RC-55).
- **Frontend build** was not run.
- **Legacy routes.** `grade-brain`, `grade-local-qwen38`, `grade-approved-*` and `grade-async` acting on bulk regions were not driven (critic M05); `GradingService.create_queued_grading_job` refuses them.
- **Open probes.** A hard kill in the middle of the `approve_clean` write loop; interleaving `approve_clean` with a concurrent per-item approval of the same draft; managed-local lease variants of the recovery probes (W11 added them for the grading-job retry only; the page-read and Recover-mid-call probes have none); the `dispatched` reservation age (900 s) against a 600 s call timeout.
- **Test hygiene.** The new tests share one database and delete from every table; they must be run only against a disposable `*_test` database.

### 11.1 Residuals and latent items from the fix wave

These come from the fixes of section 9a and from the three review passes over them. None is a proven defect with a failing test unless the text says so; each is either latent (it needs a second worker or an unusual timing) or a known edge of a fix that was deliberately not widened.

- **Two concurrent workers cannot be proven by this harness.** The supported runtime is one sequential `SimpleWorker`. The tests reach collisions through deterministic interleavings (two sessions driven in a fixed order, `RecoverMidCall`, a unit that selects an item another unit already holds), not through a real race. The cases that need a real second worker stay unproven: the two strict xfails of RC-44, the two-worker residual of F13 below, and the W11 items below.
- **W11 lease expiry does not prove the holder is dead.** For a managed-local provider the guard treats a grading job as live only while an unexpired lease is held under it. After 1,800 s without a heartbeat a hung call may still occupy the GPU, so a second call is possible; the heartbeat refusal should stop it producing a second suggestion, but that is not tested. This fails open, and needs a call longer than the lease TTL to matter.
- **W11 time-of-check to time-of-use.** The lease is released before the job's terminal commit, and there is a millisecond window between the job's `running` commit and the lease acquisition. A second worker landing in either window could close a job that is still live. The holder-id format `grading_job:<id>:<nonce>` is a duplicated literal (`grading_service.py` and the guard helper); if the two drift the guard fails open, and only the managed-local parametrisation of `Rv::test_w11_resume_item_during_a_live_call_never_closes_the_live_job_or_calls_twice` would notice.
- **An unlinked active job fails closed for good.** A worker killed between the commit that creates a grading job and the commit that links it to the item leaves an active job that no item points at. The retry cannot close it (it is not the item's own job) and the unique index refuses a new one, so the item stays stuck: it fails closed, permanently. Out of scope of W11.
- **F13 with two workers.** `_finish_processing` now marks an item still `running` as `uncertain` and pauses the run. With two workers, a live in-flight item of the other worker could be flagged this way (it fails closed).
- **A failure after the intake commit leaves a committed run with no worker.** W07 keeps the committed students' files when a later step raises (correct: the rows exist). The run stays `queued` with its files and no worker, and, since W04, a re-upload returns the existing run without enqueueing, so it does not rescue it. "Recover interrupted run" works after the 600 s stale window. Decision row 17.
- **W12(b): a leftover staged ZIP is not logged.** A Windows `PermissionError` while deleting the staged ZIP after the commit is swallowed so the 202 survives. The locked file (up to 1 GiB of student scripts) stays in `uploads/bulk_staging`, nothing logs it, and nothing sweeps the folder (`I::test_nothing_in_the_application_ever_sweeps_the_staging_folder` pins that). Follow-up: log the file name only, and add a line to the preflight to look in that folder after an upload. A hard kill leaves the same leftover (RC-28).
- **Short manifest rows are still accepted silently.** A row with fewer cells than the header leaves the identifier or name unset and falls back to the file name (RC-24, RC-33). A refusal was written in W12 and reverted, because the U+2028 case of `I::test_manifest_dialects_that_spreadsheets_write_are_refused_never_half_read` pins the old message. Fixing it means changing that pin, which needs sign-off.
- **Recover cancels a pending Stop, and Stop on an idle run strands it.** F10 and W06 stop `resume_item` from cancelling a pending Stop. "Recover interrupted run" on a stale `stopping` run still does, and `stop()` on an idle `paused` or `review_ready` run leaves it `stopping` with no worker (`Rv::test_pb5_stopping_a_run_nobody_is_working_on_does_not_leave_it_stopping`, strict xfail). RC-45.
- **`resume_item` on a paused reading run revives read-stage items run-wide.** After W04 a teacher's `resume_item` is the explicit un-pause; on a run paused during reading it revives the failed page reads of every script of the run, as run-level Resume does. Plausible from the code, not run.
- **F01 is not retroactive.** A transcript stored with `assignment_status` complete from a provider that returned blocks out of order keeps the wrong ownership, because the assignment fingerprint ignores numbering. Any transcript stored before the fix needs an offline audit of its block ownership and a teacher re-review before it is trusted. No such audit is part of this work; on a fresh cohort the question does not arise.
- **W03: identity is the name and nothing else.** The identifier is the folder or file name, or the manifest cell, with the full name kept ("Md. Karim" and "Md. Rahim" are two students). Variants of one person's name are different students, NFC and NFD spellings still differ (RC-23), and there is no roster to check against (RC-33, RC-34). A cohort imported before the fix under a truncated identifier ("Md") and re-imported into the same assessment is no longer refused as already existing (RC-22): the operator must not re-import an old cohort into an assessment that already holds it.
- **W01 names only the classes it knows.** The conversion to a named 409 (`_raise_if_named_member_failure`) matches by exception type or HTTP status for most cases and by message substring for two: a `NotImplementedError` containing "compression" (deflate64) and a `ValueError` containing "encrypted" (password-protected PDF). A different wording after a library upgrade falls back to the raw 503. Any other exception type, for example `EOFError` from a truncated deflate stream, still escapes raw (RC-18).
- **Names echoed in refusals are capped only in the new messages.** W12(e) cuts names at 200 characters in the "Could not import", duplicate-member, file-and-folder collision and manifest-line messages. Older messages (encrypted entry, entry count, duplicate identifier) still echo names unbounded.
- **A genuine file whose name starts with `._` is dropped silently.** W02 treats any basename starting with `._` as AppleDouble metadata (`I::test_a_file_that_merely_contains_a_dot_underscore_is_not_ignored` pins that a name that only contains `._` is kept).
- **EXIF (F06) covers the bulk import only.** `submission_processing._store_image_page` (the single-submission upload) still ignores EXIF, and bulk pages imported before the fix stay sideways.
- **F12 does not repair a run already stranded.** A run that the old behaviour left `paused` with every item graded stays so.
